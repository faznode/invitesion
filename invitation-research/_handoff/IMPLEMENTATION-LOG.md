### B-014 step 2 evaluation: a cached invitation shell, measured and not shipped (s21, D-039)
- **Mechanism checked first:** Next.js `15.6.0-canary.59` supports `'use cache'` behind `experimental.useCache` (default handler: in-memory LRU, 50 MB, an entry missing after its `revalidate`; key = the encoded `[buildId, function id, arguments]`, not hashed). - **Reuse proven:** in the force-dynamic, PPR-opted-out guest route, `NEXT_PRIVATE_DEBUG_CACHE` showed 50 lookups over five pages: 5 misses (first request each) and **45 / 45 hits**. A key built from full rows misses whenever a volatile column changes (the guest's `opened_count` after a view), so any real key must name render inputs only.
- **Upper bound measured:** the whole guest page in one `'use cache'` scope keyed by every input (more than any shell with per-guest holes can cache), against the unchanged build, same host, interleaved, 3 × 300 requests at concurrency 4 over five layouts: server CPU **29.6 → 28.6 ms per view** (rounds 28.0–30.2 vs 27.1–28.9, overlapping).
