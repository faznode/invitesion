## 1. Run order (sequential only)
`_tools/discovery/discover-demos.mjs` → `_tools/discovery/select-demos.py` → `_tools/capture/run-batch.sh <queue.tsv>` → `_tools/capture/summarize-captures.py` → blueprints → tier aggregates.
Never run two captures, or a capture and discovery, at the same time: Lighthouse simulation is computed from the observed trace, so CPU contention inflates TBT/LCP. Note in the session file whether the platform dev server (:3000) was running.

### 2.1 Guest page, not a preview wrapper (v1.1, session 04)
Some vendors' official "demo" links open a **preview wrapper**: a small page (theme switcher, CTA) that embeds the real invitation in an iframe. Lighthouse FCP/LCP are main-frame metrics, so a wrapper either measures the shell (Enviory: 126–129 DOM nodes, same-origin iframe, C-ENV-101…106) or nothing at all (INVI: 23 nodes, cross-origin iframe on `demo.invi.id`, Lighthouse `NO_FCP`, C-INV-101).
- Rule: if the top document has **< 200 DOM nodes and an iframe on the vendor's own site** (same host or subdomain), `summarize-captures.py` sets `wrapper=True`. Wrapper captures never feed blueprints, tiers or thresholds.
- Re-target to the wrapper's own iframe `src` (one plain fetch of the wrapper HTML, or the vendor's "Full Preview" link from discovery) with new IDs (+10): ENV → `queue-tier-a-3.tsv` (C-ENV-111…116), INV → `queue-tier-a-4.tsv` (C-INV-111…116).
- If the guest page sits behind a bot challenge for plain clients (Enviory, S-ENV-002), observe it only through the real browser; never solve or evade a challenge (R1). A captured challenge page is discarded.
- `run-batch.sh` re-attempts any ID whose Lighthouse run failed. A deterministic failure (e.g. `NO_FCP` on a wrapper) must be fixed by re-targeting, not by repeated retries.

### 2.2 Eligibility and measurement sources (v1.2, session 08, D-023)
`_tools/capture/eligibility.py` decides what each capture may support. `summarize-captures.py` keeps every capture in `captures-summary.csv` with `coldload_eligible`, `structure_eligible` and `eligibility_reasons`; `dossier-digest.py` computes medians from eligible captures only; `commit-guard.sh` runs `eligibility.py --check`.
- **Curated register first.** `benchmark-exclusions.csv` (`capture_id,scope,page_class,reason,decision,evidence,revisit_when`) always wins: heuristics never override a row, they only report findings. `scope=all` = no benchmark use; `scope=structure` = no structural or interaction use while the Lighthouse cold load stays valid (allowed only with `page_class=guest_page`). Invalid scopes or classes, unknown or malformed ids, empty decisions, duplicate and conflicting rows are errors and are applied conservatively (excluded) until fixed.
- **Page class:** curated row > `kind` (marketing, catalog) > wrapper heuristic (§2.1; excluded until curated) > `kind=demo` → guest page. Lighthouse success never turns a wrapper, catalog or marketing page into a guest-page sample.
- **Cold-load eligible** = guest page + Lighthouse OK with the protocol settings (12.8.2, 4× CPU, 150 ms RTT, 412 px mobile) + robots allowed at capture time + no `scope=all`. **Structure eligible** = guest page + robots allowed + no `scope=all|structure`. A capture whose robots.txt answered 5xx/429 (or disallowed) without a `scope=all` row is an error (D-022).
- **Provisional evidence (s13, D-031).** `benchmark-provisional.csv` (`capture_id,decision,question,reason,evidence,revisit_when`) lists captures that wait on an open owner / reviewer question. They are excluded from the **unconditional** population (`coldload_eligible`, `structure_eligible`) and kept in a separate **sensitivity** population (`*_eligible_sensitivity`, which applies the exclusion register only). Unconditional claims use only the unconditional population; sensitivity results are written to separate files (`sensitivity/*-incl-provisional.csv`, `coverage-summary.md` § Sensitivity, `dossier-digest.py --sensitivity`) and labelled. A row needs a D-NNN decision and a Q-ONN question; invalid rows are errors and still exclude. Today: C-ENV-111…123 (Q-O09).
- **Unique coverage** counts `theme_key`s (host + path + theme query parameters such as Enviory's `tpl`; guest parameters `to`, `code`, `kpd` … dropped), never attempts; `theme_attempt`/`theme_attempts` number the retries. Aggregates take the **median per theme first**, then across themes, and report both counts. A "valid demo" for Wave 1 = a cold-load-eligible unique theme; structure limits are recorded beside it.
- **Two sources, never mixed:** `lh_*` = Lighthouse cold load (Lighthouse never clicks); `cdp_visit_*` = our CDP session over the whole visit (load + REA scenario + cover click + scroll, unthrottled). `*_bytes` are exact; `*_kib` = bytes / 1024, rounded. Dossiers written before s08 say "KB" for these KiB values.
- **Cover facts are separate:** `cover_detected` (text detector; "not detected" ≠ no cover, e.g. C-IVT-102/103), `click_attempted`, `click_method` (`trusted…` = D-016, otherwise pre-D-016), `gate_opening` (`verified_open` = trusted click and gate gone; `unverified_open` = gate gone after a pre-D-016 click; `gate_persisted`; `no_click`; `no_cover_detected`) and `audio_playback` (always `not_measured`: no capture records media state). Opening or post-open interaction claims need `verified_open` or an explicit limitation.
- **Summary schema v2 renames:** `requests` → `cdp_visit_requests`, `kb_total` → `cdp_visit_kib`, `kb_<type>` → `cdp_visit_kib_<type>`, `third_party_hosts` → `cdp_third_party_hosts`, `font_files` → `cdp_font_files`, `wrapper` → `wrapper_heuristic`, `cover_clicked` → `click_attempted` + `click_method` + `click_landing`. New: `lh_requests`, `lh_bytes`, `lh_kib*`, eligibility, theme and cover columns. `features` no longer infers `coverGate` from the click.
- **Masking:** `dossier-digest.py` prints no values for `scope=all` rows and non-guest pages unless `--show-excluded` is given, so a pasted table cannot carry numbers that must not be cited.
- **Regression tests:** `python3 -B invitation-research/_tools/capture/test_eligibility.py` (offline, brief 05 B3 cases).

### 2.3 Measurement profiles (v2, session 13, D-032)
`_tools/capture/capture-profile.mjs` defines one **profile** per measurement population. `capture.mjs --profile <name>` (5th queue column in `run-batch.sh`) applies it to every channel: the CDP session, REA's scenario `environment` and Lighthouse. v2 captures carry a `measurement` block (protocol, profile, viewport, DSF, motion, method, Lighthouse screen and motion, `cdp_reapply`, `emulation_verified`, `emulation_mismatches`, the final and during-scenario probes); `summarize-captures.py` copies it into `captures-summary.csv`.

| Profile | Protocol | CSS viewport | DSF | `prefers-reduced-motion` | Method |
|---|---|---|---|---|---|
| `v1-412` (default) | v1.2 | 412×915 | 2.625 | not set | §2 unchanged: REA scenario + REA inspect / bundle + CDP structure pass + Lighthouse |
| `v2-412` | v2 | 412×915 | 2.625 | `no-preference` (set) | lean: REA scenario + CDP structure, layout and motion probes + Lighthouse; no REA inspect / bundle |
| `v2-360` | v2 | 360×800 | 3 | `no-preference` | lean |
| `v2-390` | v2 | 390×844 | 3 | `no-preference` | lean |
| `v2-412-rm` | v2 | 412×915 | 2.625 | `reduce` | lean; Lighthouse's Chrome starts with `--force-prefers-reduced-motion` |

- **Separate populations.** Profiles are never pooled. Tier files (§4) use `v1-412` only. v2 results go to `viewport/`: per-profile aggregates and per-theme paired deltas against the same-session `v2-412` control; a delta exists only when both profiles of a theme are eligible for the metric's source (Lighthouse → cold-load, layout / motion → structure). `v2-412` is not merged with `v1-412` either (same viewport, different method and session).
- **Lighthouse channel, per capture:** `eligibility.lighthouse_status()` requires the Lighthouse screen to equal the profile (width, plus height and DSF for v2) on top of the §2.2 settings. Lighthouse has no motion setting; the switch for `v2-412-rm` is proven by `verify-profiles.mjs` (the page inside Lighthouse's Chrome reports `reduce`).
- **CDP channel, per capture:** after REA's scenario and the re-apply, `EMULATION_PROBE_V2` must match the profile (screen size, DPR, motion, Android UA; `innerWidth` follows the page's own viewport meta, so it is recorded, never verified) → `emulation_verified`. An unverified CDP emulation removes the capture from structure, layout and motion evidence only. Its Lighthouse cold load stays eligible, because Lighthouse runs its own Chrome whose screen is checked above (D-032).
- **Re-apply after REA (s13 fix).** REA's connect-mode disconnect wipes the capture session's device metrics and emulated media, and Chrome treats an identical re-sent `Emulation.setDeviceMetricsOverride` as already applied: the page stayed at DPR 1 with an 800×600 screen. v2 therefore sends `clearDeviceMetricsOverride` → `setDeviceMetricsOverride` → `setEmulatedMedia` (`emulationCommands()`), recorded as `cdp_reapply: clear + set`.
- **During REA's scenario** the page runs under REA's own emulation: viewport, DSF and motion match the profile, while `screen.*` reports the 800×600 headless window (REA's scenario schema has no mobile flag). The before-open probes run in that window; the state is recorded as `emulation_during_scenario`.
- **Touch is not emulated in the CDP session** (v1 or v2; `coarsePointer: false` is recorded). Lighthouse's mobile emulation does enable it: in the external npm package `lighthouse@12.8.2/core/lib/emulation.js`, `emulate()` sends `Emulation.setTouchEmulationEnabled` with `enabled: mobile` (re-checked s14 against the upstream `v12.8.2` tag; not a path in this repository). CSS that depends on `(pointer: coarse)` is therefore not reflected in the layout probe.
- **v1.2 disclosure.** `v1-412` keeps its single pre-s13 call, so v1.2 stays reproducible. Its post-REA passes (cover click, scroll, after-open fingerprint) therefore ran at 412 CSS px with DPR 1 and an 800×600 screen: all 32 v1.2 captures that recorded `rea.emulation` show the wiped state (`width 500, dpr 1`) after REA, and `verify-profiles.mjs` (channel `cdp-after-rea`, informational for v1) reproduces the state after the identical re-send. CSS-px layout and the structure fingerprint are unaffected; DPR-dependent behaviour (`srcset`, `resolution` media queries) was not emulated in those passes. Lighthouse is unaffected.
- **Pilot.** C-WEV-201…204 (theme `espresso`, the four v2 profiles, 2026-11-04 12:39–12:45Z) ran before the fix: Lighthouse eligible, CDP structure excluded (`emulation_verified: false`). They keep their IDs, files and status. s14 (D-032 amended by D-033) re-captures the theme with new IDs C-WEV-225…228 (`queues/queue-v2-s14-espresso.tsv`) so its structure, layout and motion channel exists at all four profiles.
- **Layout probe** (`LAYOUT_PROBE`, after open): horizontal overflow (document `scrollWidth − innerWidth`; elements past the viewport without a clipping or scrolling ancestor), visible text below 12 px, interactive targets under 24×24 CSS px (WCAG 2.2 SC 2.5.8 minimum; the spacing exception is not evaluated), zoom blocked by the viewport meta. **Motion probe** (`MOTION_PROBE`, before and after open): animations from `document.getAnimations()` (CSS animations, transitions, Web Animations), running and infinite counts, active GSAP tweens, playing videos.
- **Verification:** `node _tools/capture/verify-profiles.mjs --out raw/_setup/<file>.json` on a local 127.0.0.1 page (no competitor contacted): CDP channel, CDP-after-REA channel (gating for v2) and Lighthouse channel. Records: `raw/_setup/profile-verification-2026-11-04.json` (CDP + Lighthouse, before the fix) and `raw/_setup/profile-verification-2026-11-04-reapply.json` (all three channels, after it). Offline tests: `capture-profile.test.mjs`, `test_eligibility.py` (`MeasurementProfiles`), `test_benchmark_pack.py` (`Viewport`). s14 re-ran it in a fresh sandbox before resuming the batch: `raw/_setup/profile-verification-2026-11-04-s14.json`, all channels OK.
- **Fixed order (s14 limit).** Within a theme the queue always runs `v2-412` first, then `v2-360`, `v2-390` and `v2-412-rm`, about a minute apart. A paired delta is therefore also a difference in run order: a CDN or server cache warmed by the control visit, and host drift (benchmarkIndex varies between consecutive runs), can move timing metrics in one direction for every later profile. Timing deltas (performance, LCP, TBT) support no causal viewport or motion claim. Layout probes (overflow, small text, small targets) and motion counts are not timing measurements and are the robust part of the batch. A counterbalanced queue (reversed order for half the themes) is the check to run before any timing claim.
- **Own builds (D-033, s14).** For our own pages the product build is part of the population: `22ed99e` (C-INV-001…005) and `0b5eb1b` (C-INV-006…015) are never pooled, and their hosts differed too (benchmarkIndex 1,415.5–1,470 vs 820–1,251.5, `viewport/lighthouse-environment.csv`).

## 4. Tier labelling and aggregation
- Every queued demo gets a tier (`basic | premium | signature`) from the vendor's own catalog label or price, with an evidence ID, in `tiers.csv` (`capture_id,tier,evidence`). Unlabelled demos are `unknown` and excluded from tier thresholds.
- `tier-aggregates.csv`: per tier and metric, **median, p75, best-in-class** over **cold-load-eligible competitor guest pages** (§2.2), median per theme first, with theme and capture counts. Metrics from Lighthouse fields only: perf, a11y, LCP, CLS, TBT, `lh_requests`, `lh_kib`, `lh_kib_script`, `lh_kib_image`, `lh_kib_font`, `lh_kib_media`. Post-visit CDP values (`cdp_visit_*`, `cdp_font_files`, `cdp_third_party_hosts`) are reported separately with their source and never mixed with them. TBT is a lab proxy, not INP (§3.7).
- Parity threshold for the harness (Phase 7.6) = the tier median per metric (lower is better for time/bytes; higher for scores). "Beyond" = better than p75. Thresholds record `n` and the capture IDs used.

## 5. Blueprints (structure and measurements only)
`blueprints/<capture-id>.md`: section sequence, component types, interaction patterns, motion character and parameters (durations, easings, triggers — from REA bundle evidence and observation), layout grid, type pairing (family names only), palette logic (described, not sampled into our repo), imagery style, Indonesian copy conventions (described, never quoted at length), asset budget from the summary. No competitor HTML/CSS/JS, images, fonts, audio or copy (R2).
