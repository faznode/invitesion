### ADR-O01 — Template art is template-owned; invitation config stays strict (Q-O01)
- **Status:** ACCEPTED (s08) · **Confidence:** high (runtime-verified defect).
- **Context [OBSERVED]:** `detailConfigSchema` (`lib/invitation/detail-config.ts`) is `.strict()` at the top level and has no `art` key; a runtime check returns `unrecognized_keys: ["art"]` for `{ art: {…} }`. `template-sync.ts` writes `defaultConfig = { ...preset, art }` for every catalog template, and `create.ts` keeps the template defaults only `if (parsed.success)`, so **every invitation created from a catalog template starts from `{}`** and loses its preset (palette, sections, copy). `templates.ts:361` parses the same way.
- **Options:** (a) add `art` to the invitation schema (copies shared asset sets into every invitation); (b) split `art` from the preset before validation and resolve art by template; (c) move `art` to its own template column; (d) make the schema permissive (rejected: loses validation of user config).
- **Decision:** (b) now, (c) as the follow-up: validate `{ ...preset }` without `art`, keep `art` template-owned and resolved through `template_id`; the strict invitation schema stays. An optional per-invitation `artOverride` key may be added later (additive).
- **Consequences:** P0 fix in `create.ts` (and the `templates.ts:361` parse) with a regression test "catalog template → created invitation keeps preset keys". Existing invitations are **not** rewritten automatically (their config may already hold user content); a host-triggered "re-apply theme defaults" is the safe repair path.
- **Revisit:** the renderer needs per-invitation art edits → introduce `artOverride`; template art moves to a CDN manifest → (c) becomes the column/manifest reference.

### ADR-O02 — `lib/pricing.ts` is the price source of truth; marketing must show it (Q-O02)
- **Status:** ACCEPTED (s08) · **Confidence:** high on the conflict, medium on future packaging.
- **Context [OBSERVED]:** `lib/pricing.ts` charges IDR 149,000 (standard) / 299,000 (premium), one-time, 12 months active (F-064, F-085). ## Architecture ADRs (session 09)

### ADR-A1 — Keep the Next.js stack; no Rust service now; fix the render path inside Next.js
- **Status:** ACCEPTED (s09, 2026-11-03) · **Confidence:** medium (lab spike on one 2-vCPU host; effects are far larger than the round-to-round spread, but production CPU, network, compression, middleware and database distance differ).
- **Context [OBSERVED]:** s08 left a Next-only run and an unfinished Rust run. s09 fixed the spike tooling (validity thresholds, failing exit codes, per-PID sampler, database snapshots) and ran a matched comparison in two rounds with reversed order: the product page (`next`), a Next.js route doing the product's loader once with minimal HTML (`next-min`), and the Axum spike doing the same queries with the same minimal HTML (`rust`); same database, fixture, pool size 10, warm-up and workload (`../08-backend-rust-plan/spike/`). Round 1: read spike 36 / 242 / 1,156 req/s; server CPU per page ≈ 30 / 4 / 0.3 ms; at 1,156 req/s Postgres used 112 % of a core and Rust 39 %. RSVP burst 261 / 359 / 1,439 req/s with RSVP events equal to accepted writes on every arm. The view-dedupe race (duplicate VIEW rows) and the allowance overwrite reproduced on every arm. The product page also calls the loader twice per request and answers 200 for unknown guests. A snapshot-only variant with the loader in React `cache()` (two rounds) left server CPU per page at 25–31 ms (within the spread) and cut Postgres CPU per page from ≈ 3.1–3.2 to ≈ 2.0–2.2 ms: the server cost is the full template render (≈ 85–90 %), not the duplicate load.
- **Options:** (a) keep Next.js and fix the render path; (b) a Rust service for the guest page behind the same URL (strangler); (c) rewrite the backend in Rust.
- **Decision:** (a). (b) is deferred behind explicit triggers; (c) is rejected (no measured need, duplicates every domain rule, cannot render the React template system).
- **Consequences:** B-014 (cached invitation-level render with per-guest parts rendered per request, one loader call for the database, no Clerk / locale cookie on `/i/*`) is the performance lever, measured against the spike (target ≤ 2 × the `next-min` server CPU); B-017a makes view tracking atomic; B-007 and B-011 stay P0; telemetry (`../08-backend-rust-plan/README.md` §6) precedes any further performance claim; the spike stays as test equipment, not product code; the project skill `invitesion-rust-backend` (no vetted third-party Rust skill is locked) records the triggers, the measurement method and the rules for an incremental service, so a future agent does not start a rewrite without them.

### D-042 — What a theme write may change: the Premium palette rule (B-041, s26 Phase C)

### D-043 — RSVP writes through the Rust API: keyed retries, shared limits, a trusted-proxy address (R-03; code s27, completed s28)
- **Context [OBSERVED]:**
  - ADR-A2 allows one writer per column group and no fallback after an ambiguous write; a fallback after a timeout could write a second time for a request the first writer committed.
  - RSVP is the core guest write and had no limit (B-013). Guests arrive in WhatsApp blasts, often many behind one carrier NAT, and IPv6 subscribers routinely hold a whole /64.
  - `X-Forwarded-For` is appended by every proxy; only entries written by trusted proxies are facts. Vercel's edge replaces the header with the client's address alone.
  - The s27 code minted a form key per rendering but sent none from the host's dashboard, retried nothing, threw on a transport failure (a generic error page), and read the leftmost forwarded entry or `X-Real-IP`.
- **Decision:**
  - (1) Every RSVP write to the API carries an `Idempotency-Key`, recorded with the response in the write's own transaction (`api_idempotency_keys`, kept 24 h). The guest page mints one per rendered form; the writer mints one when a form has none and for every host override.
  - (2) An unknown outcome (status 0, any 5xx) is sent exactly once more under the same key: a committed write replays, an uncommitted one writes once. The other writer is never tried. If the retry is unknown too, the guest sees "unconfirmed" and the re-rendered form carries the same key (`?rsvp=retry&rsvpk=`), so the next send writes at most once; the host sees `?error=unconfirmed` and the list shows the state. Codes and status are logged, never guest data.
  - (3) Fixed-window limits in `api_rate_limits`, shared by every instance: per link (default 10 / 600 s) and per address (60 / 600 s), refused with 429 and `Retry-After`; the guest's notice says how many minutes. Replays answer before the limiter.
  - (4) The address is the `X-Forwarded-For` entry `TRUSTED_PROXY_HOPS` places from the right (default 1; 0 trusts no header; an unreadable value trusts none). Only IP literals are sent. The API keys IPv4 (and IPv4-mapped IPv6) by address and IPv6 by its /64, and stores an HMAC of the key under the service secret, never the address.
  - (5) Refusals map to the notices the TypeScript writer gives (closed, invalid, the event or question to fix, busy). The owner check's 403 sends the host to sign-in, as `context()` does; 400 and 401 are deployment errors and propagate.
  - (6) Migration 0016 is additive and written only by the API; drizzle-kit stays the single migration owner. Stored guest shapes are unchanged.
- **Rejected:**
  - a fallback to the TypeScript writer after a failure: it could write twice;
  - the leftmost forwarded entry or `X-Real-IP`: client-controlled unless a proxy is contracted to set them;
  - per-address IPv6 limits: one line can rotate through 2⁶⁴ addresses;
  - storing or logging addresses (UU PDP).
- **Limits:**
  - Concurrent sends of one form each pass the limiter before one commits, so at the boundary a twin can see "busy" while the other saved; sequential re-sends replay before the limiter.
  - The per-address limit is only as good as the deployment's proxy contract; without a trusted proxy (`0`) only the per-link limit applies.
  - A double click on a dashboard control is two overrides with one result (two RSVP analytics rows); the key covers one override's retry.
- **Evidence:** E-059 (`verify-rsvp-api` through both call sites and the running binary, with negative controls; unit tests for the writer, the client and the address contract).
- **Revisit:** a deployment behind other proxies (set `TRUSTED_PROXY_HOPS`), or limits that real traffic proves too tight or too loose.

### D-044 — Wishes: moderation, replies and visibility, written through one writer (R-04; s28)
- **Context [OBSERVED]:**
  - B-028: `guest_messages.is_hidden` existed and the guest page already skipped hidden rows, but nothing set the flag. Hosts could not approve, hide, delete or reply, so every wish was listed and counted.
  - B-013: wishes had no write limit. B-017: the guest page's newest-wishes list and count had no index.
  - ADR-A2 and D-043 fix the slice mechanics: one writer per column group, an `Idempotency-Key` on every API write, one retry under the same key, no fallback.
- **Decision:**
  - (1) Three states from the existing column plus one timestamp: **VISIBLE** (`is_hidden` false), **PENDING** (hidden, `reviewed_at` null: the guestbook was moderated when the wish arrived), **HIDDEN** (hidden by the host, `reviewed_at` set). `is_hidden` keeps its meaning, so the guest page's rule stays "not hidden".
  - (2) Two host settings in the guestbook section: `moderation` (default off) stores new wishes PENDING, and the form tells the guest; `visibility: 'host'` (default `public`) keeps every wish for the hosts: the page shows the form and no list, and the loader runs no wish query. An unreadable section reads as open, unmoderated and public.
  - (3) Host operations on `/dashboard/invitations/<id>/wishes`: show (approve a pending wish or restore a hidden one), hide, delete, reply (trimmed, at most 1,000 UTF-16 units; blank clears). A reply is stored on any wish and rendered only under a visible one. Only the invitation's owner; administrators sign in; the wish must belong to the invitation.
  - (4) One pure decision, `lib/invitation/wish-decision.ts`: the switch first, then the message (trimmed, 1–1,000 UTF-16 units, no U+0000), then moderation. `contracts/vectors/wish-decisions.json` runs it in both languages.
  - (5) Writer selection `BACKEND_WISHES` (default `next`) with D-043's contract: the guest form's key comes from the per-render key helper; each host action mints its own key, so a retried delete replays instead of answering "not found". Unknown outcomes are retried once and then shown as `?wish=retry&wishk=`. Limits are per link (5 / 600 s) and per address (60 / 600 s, IPv6 per /64), shown as `?wish=busy&wishr=`. A form key reused with another message is treated as a new wish and sent under a fresh key, not refused.
  - (6) Migration 0017 is additive (`reviewed_at`, `host_reply`, `replied_at`, index `guest_messages_invitation_visible_idx (invitation_id, is_hidden, created_at)`); drizzle-kit owns it. The guest page still shows the newest 50 visible wishes, oldest first.
- **Rejected:**
  - a separate status column: a second source of truth beside `is_hidden`, and a changed read rule for the guest page;
  - refusing a reused form key with a changed message: a guest who brings an old page back would lose what they typed;
  - hiding the form on a hosts-only guestbook: the wish still reaches the hosts, and the form says who reads it.
- **Limits:**
  - The TypeScript writer applies no limits. It is the rollback path until the rollout removes it.
  - Concurrent twins at a limit boundary behave as in D-043.
  - A moderated guestbook shows a new wish to nobody until the host approves it. The notice says so.
- **Evidence:** E-060 (`verify-wishes-api` through both writers and the running binary, `EXPLAIN` on the guest page's queries, five negative controls; unit and vector tests in both languages).
- **Revisit:** limits that real traffic proves wrong, or a request to show pending wishes to their author.

### D-046 — A host's idempotency key replays only to its owner, on the same invitation and resource (s29, before any Rust rollout)
- **Context [OBSERVED]:**
  - At `2c5fcde` the three host writes (RSVP override, wish moderation, wish reply) looked up their key under a scope naming only the resource (`rsvp:host:<guest>`, `wish:host:<wish>`, `wish:reply:<wish>`), and before the ownership check.
  - Reproduced in s29 against the `2c5fcde` binary with the real service signature and valid owner tokens (E-062): another customer reusing the owner's key got the cached answer (200, `Idempotent-Replayed: true`; for a reply, the host's text), and so did a reuse under another invitation and after a lost delete. With a changed body the answer was 422 `idempotency.key_reused`, which reveals that the key exists. No refusal wrote anything.
  - Through the product the dashboard mints a random key per host action and only the server holds the service secret, so using this needs a leaked key or a future caller that chooses keys. Isolation must not depend on keys staying secret, and ADR-A2's rollout must not start with it open.
- **Decision:**
  - (1) A host write is recorded under `<operation>:<owner users.id>:<invitation>:<guest or wish>` (`idempotency::host_scope`). The scope is built after the owner is resolved from the verified token and administrators are refused, and before the lookup.
  - (2) The lookup stays before the row lock, so the same owner's retry on the same path with the same body replays, including a delete whose row is gone (D-044's contract).
  - (3) Anyone else's request finds no record under its own scope. It is judged afresh and refused by the ownership check: 404, nothing written, no key recorded, no cached answer, and no 422 that could reveal the key.
  - (4) Guest scopes are unchanged (`rsvp:guest:<guest>`, `wish:guest:<guest>`): the link is resolved before the lookup, so the scope already names the guest it resolves to.
  - (5) No migration: a host scope is at most 43 characters (`varchar(120)`), and no query changes.
- **Rejected:**
  - moving the lookup after the ownership check: a retried delete would answer 404 instead of replaying;
  - a principal column beside the scope: a migration for what the primary key `(scope, key)` already expresses;
  - hashing the principal into the request hash: another customer's request would still find the record and answer 422.
- **Limits:**
  - Keys recorded under the old scopes stop replaying when this deploys. No Rust writer is live (every `BACKEND_*` defaults to `next`), so no retry is affected.
  - An owner who loses an invitation can still replay their own earlier answers for up to 24 hours. Nothing new is disclosed.
- **Evidence:** E-062.

### ADR-A3 — The browser writes only through same-origin Next.js routes; the Rust API stays private (B-024's scanner)
- **Status:** ACCEPTED. Taken with B-024's code at `33c0b12` (s33), which cites it, but not recorded there; recorded in s34 after a review of that code (self-review under ADR-O09). It settles 09 §8's open item: browser access "needs its own ADR covering CORS, CSRF and rate limits".
- **Context [OBSERVED]:**
  - Every API call carries the internal HMAC signature, and the API sends no CORS headers (09 §8). Only the Next.js server holds the signing secret.
  - The scanner is the first write the browser sends with `fetch`: an outbox that resends batches after a weak signal or a reload. Every earlier write is a server action, which Next.js refuses cross-site by comparing `Origin` with the host.
  - A scanner page stays open through an event. Server action ids change with each build, so a page opened before a deploy may no longer reach them (unless skew protection keeps the old deployment). The outbox must also tell an unknown outcome (resend unchanged) from a refusal (drop it), which needs status codes.
- **Options:**
  - (a) expose the API to the browser: CORS for the app's origin, the Clerk token sent by the browser, and a replacement for the service signature, which a browser cannot hold;
  - (b) a same-origin route handler in Next.js that checks the request, then calls the roster facade, which reaches exactly one writer from the server;
  - (c) a server action for the scanner's batches.
- **Decision:** (b). Rejected: (a) adds a second, public way into the API, with CORS and browser-facing limits to maintain, for nothing B-024 needs; (c) is bound to one deployment and answers without status codes.
- **Rules** (`app/api/invitations/[id]/checkins/route.ts`):
  - **CSRF before the session.** `sameOrigin()` (`lib/api/same-origin.ts`) runs first. `Sec-Fetch-Site` must be `same-origin` when present; without it, `Origin` must name this host; with neither, the request is refused (403 `CROSS_SITE`). Then JSON only (415), so a cross-site form or any other simple request never reaches the body. Neither the route nor the API sends CORS headers.
  - **Session and owner.** A Clerk customer session is required (401; an administrator gets 403). The owner is the session's user, never a submitted id, and each writer checks ownership again inside its transaction.
  - **Flag first.** With `FLAG_GUEST_PASS` off the route answers 404 before reading the body.
  - **Input.** A strict schema: the batch key (8–100 printable characters) and 1–50 scans, each with a token of at most 200 and a scan time of at most 40 printable ASCII characters. Printable ASCII also keeps the batch's canonical JSON byte-identical in both writers, which the idempotency hash needs.
  - **Rate limit.** 120 batches per host and invitation per 60 s (`RATE_LIMIT_CHECKIN`), counted in `api_rate_limits` with the API's statement before any writer runs (429 with `Retry-After`). A batch counts once, whatever its size.
  - **One writer.** The roster facade (`BACKEND_ROSTER`, D-052) calls the TypeScript writer in-process, or the API with the service signature, the owner's token and the batch key as `Idempotency-Key`. An ambiguous failure is resent once under the same key, then answered 503 `CHECKIN_UNCONFIRMED`, and the outbox keeps the batch unchanged. There is no fallback between writers.
  - **Answers.** `Cache-Control: no-store`. Each scan gets an outcome; only `checked-in` and `already` carry a display name and a time.
  - The manual fallback stays a server action: one tap, online, never queued.
- **Consequences:** a scan travels browser → Next.js → writer, one hop more than a direct call, within one region. The route is the one place for G-044's usher roles, per-device limits or an audit trail.
- **Revisit:**
  - a scanner that cannot hold a web session (a native or third-party app): a device credential under its own ADR;
  - G-044: the route checks the usher's grant instead of ownership, and the exposure stays as it is;
  - the desk target (≤ 3 s per guest, `07-canonical-flows.md`) missed on a device because of the extra hop;
  - a browser change to `Sec-Fetch-Site` or a Next.js change to its server-action origin check (re-check `sameOrigin()`).

### D-056 — The guest pass: a signed QR on the personal link, a scanner with an offline outbox, one arrival per guest across both writers (B-024 + I-01 / I-27 / G-027; code s33, completed s34)
- **Context [OBSERVED]:** before B-024 the manage centre called QR "a roadmap item", and arrivals were the guest list's check-in, which in both writers overwrote `checked_in_at` and added a CHECKIN row on every call. 06's acceptance: the QR carries an HMAC token, not the guest id; check-in is idempotent; forged, expired or replayed tokens are rejected; there is a manual fallback; the greeting shows the display name only; with the flag off the QR and the scanner are hidden, records are kept and tokens are inert. 07 asks for ≤ 3 s per guest at the desk, including with a weak signal (I-27). The code at `33c0b12` cites D-056, but the record was missing. s34 found four defects, fixed in (3), (4), (6) and (7) below. After a lost answer the TypeScript writer alone turned a first arrival amber. The manual fallback and the list's check-in could record one arrival twice. The site-wide `Permissions-Policy: camera=()` denied the scanner its camera on every deployment. The API's definite 503 for a missing secret was resent and reported as an unknown outcome.
- **Decision:**
  - (1) **The pass.** `IVP1.` + base64url(pass id, 16 bytes ‖ expiry, u32 big-endian ‖ the first 16 bytes of HMAC-SHA256(secret, `invitesion.guest-pass.v1` ‖ 0x00 ‖ pass id ‖ expiry)), 53 characters in all. The pass id is `guests.pass_id`, never the guest id. Migration 0022 adds it: 122 random bits as 32 hex characters, set by the database for every guest. `GUEST_PASS_SECRET` (≥ 32 bytes) signs; `GUEST_PASS_SECRET_PREVIOUS` is also accepted during a rotation. A read checks the shape, then the MAC against every accepted secret, then the expiry, so a forged token never learns whether it would have expired. A pass expires two days after the latest event time, or 30 days after the next UTC midnight when no event is dated. The rules exist in both languages (`lib/invitation/guest-pass.ts`, `services/api/src/roster/pass.rs`), pinned by `contracts/vectors/guest-pass.json`.
  - (2) **Where it shows.** Only on the guest's personal link (`/i/<slug>/<guest>/pass`, linked from the personal page), with the flag on, the invitation opted in (`config.checkInSettings.enabled`) and a signing secret set. The public page never shows a pass.
  - (3) **A guest arrives once.** Every check-in path (a scanned pass, the scanner's manual fallback, the guest list's check-in) stores the first time only and writes one CHECKIN event (`source: pass` for scans). A later check-in writes nothing, and the scanner answers `already` with the stored time. Undo still clears the time, so a check-in after it counts again. A scan locks its guest's row inside the roster lock (D-052), so two desks scanning one guest at once record one arrival.
  - (4) **A resent batch replays its first answer, through either writer.** Every batch carries the scanner's key. Both writers record it with the answer in `api_idempotency_keys` under the same scope (`roster:pass-checkins:<owner>:<invitation>:0`), the SHA-256 of the batch's canonical JSON and the same 24-hour retention; `lib/idempotency.ts` is the TypeScript side of `services/api/src/idempotency.rs`. So a resend replays across a flip of `BACKEND_ROSTER` too, and a different batch under a used key is refused (422 `KEY_REUSED`).
  - (5) **Scan time.** A queued scan keeps its own strict UTC time within the last day. An older one is stored a day before now; a future, malformed or absent one as now (vectors `scanTimes`).
  - (6) **The scanner (I-01 / I-27).** It reads the camera (`BarcodeDetector`, with jsQR as fallback) or a handheld scanner's keystrokes. Scans enter a device outbox (`checkin-queue.ts`): local storage per invitation, at most 2,000 scans, tokens and times only, never names. A batch of at most 50 is resent unchanged under its key until answered and leaves storage only once confirmed. A stored batch that lost a scan is re-formed under a new key, never resent as a different batch. The greeting is full screen: green for a first arrival, amber "Sudah check-in" with the first time, red for refusals, showing the display name only. Names come from the page, which holds them under a one-way key of each pass id, so a scan can be named offline. The manual fallback (search by name) is a server action, online only, and refused where the host turned manual check-in off or requires the QR. Only the scanner page may use the camera (`Permissions-Policy: camera=(self)` there, `camera=()` everywhere else), and both links to it (the guest list, the manage centre) load the page in full, because a client-side navigation keeps the previous document's policy.
  - (7) **Errors.** A refusal is never resent. The API's 503 `guest_pass.not_configured` comes before any write and maps to "not configured", not "unconfirmed".
  - (8) **Off.** `FLAG_GUEST_PASS` defaults off. Off hides the pass and the scanner, the route answers 404 (every pass is inert), and stored check-ins stay.
  - (9) **Exposure:** ADR-A3.
- **Rejected:** the guest id or slug in the QR (enumerable: anyone could print a pass for any guest); a stored random token compared as it is (a database dump alone would hold every valid pass, whereas the MAC also needs the secret); overwriting the time on every check-in (the baseline, where a stale list or a second desk recorded one arrival twice); answering `already` after a lost answer in one writer while the other replays (a false amber screen, and writers that disagree); a fallback from Rust to TypeScript after a timeout (a second writer, D-043); guest names in the device's storage (a lost phone would carry the guest list).
- **Limits:** acceptance on real devices (cameras, handheld scanners) is EXT and not run. s34's browser check ran without a physical camera: the handheld-scanner field, the manual fallback, and the camera path through Chrome's fake capture device showing a pass (jsQR; `BarcodeDetector` is absent on Linux). The signed-in path with real Clerk keys is DA-01, NOT RUN: s34's evidence stubs Clerk. The desk target (≤ 3 s per guest) is not measured on a device. Until G-044 only the owner can scan. If the manual fallback and another desk check one guest in within the same moment, the manual answer can show green while the other desk's time is kept; the arrival is still recorded once. With `BACKEND_ROSTER=rust` the API needs the same `GUEST_PASS_SECRET` (and `_PREVIOUS`) as Next.js, which signs the passes.
- **Evidence:** E-074.
- **Revisit:** G-044 (usher roles: the route checks a grant, ADR-A3); device acceptance (EXT); the flag after DA-01; the `BACKEND_ROSTER=rust` rollout (as D-052); a written rotation runbook should a secret leak.

### D-057 — An invitation's team: per-invitation grants for co-hosts and ushers, joined by a one-time link, checked on every request and before any stored answer (G-044; code s34 export, completed s35)
- **Context [OBSERVED]:** until G-044 every host surface was owner-only (`requireOwnedInvitation`, the writers' owner checks). 06's acceptance: role-scoped access, ushers see check-in only, authorisation tests per role, a signed-in check EXT; rollback: revoke roles, owner-only access. The s34 export (`1c0b1d7`) held migration 0023, the team rules in both languages, the join flow, the shared dashboard and grant-aware checks, and cited D-057, which was not recorded. s35 measured it and found: (1) **a revoked member could read a stored answer.** `passCheckinNext` and all twelve Rust host writes (nine roster, the RSVP override, wish moderation and reply) looked up the idempotency key before the access check, so a revoked usher replaying a check-in batch got the guests' names back; (2) the global guest list's actions asked the writers only, which check the grant but not `FLAG_TEAM_ACCESS`; (3) five read entries (guest list, import, insights, wishes, the export) did not refuse an administrator before the guard; (4) the guard counted a grant held by an account later made an administrator or deleted; (5) four unit pins still named the pre-G-044 owner checks, so the checkpoint failed 5 of 564 tests.
- **Decision:**
  - (1) **Roles and capabilities** (`lib/invitation/members.ts`, mirrored by `services/api/src/members.rs`, pinned by `contracts/vectors/member-roles.json`):

    | Capability | Owner | Co-host | Usher |
    |---|---|---|---|
    | `checkin`: the desk, its route and the manual fallback | yes | yes | yes |
    | `guests`: guest list, add / import / undo, invited events, RSVP override, registration link and decisions | yes | yes | no |
    | `wishes`: moderate and reply | yes | yes | no |
    | `insights`: insights and the guest export | yes | yes | no |
    | `manage`: content, theme, settings, the team, checkout, publication, destructive actions | yes | no | no |

  - (2) **Storage.** Migration 0023 `invitation_members`: one row per join link, which becomes the grant when accepted (`user_id`, `accepted_at`) and ends with `revoked_at`. Role `cohost` or `usher` (check constraint); label 1–60 characters, the owner's own note; the link's SHA-256 (hex, unique) and never the secret; expiry seven days after creation; a partial unique index allows one live grant per invitation and account. Deleting the invitation cascades; an account with a grant cannot be hard-deleted (accounts are soft-deleted).
  - (3) **The link.** Only the owner (`manage`) mints or revokes, at most 20 live rows per invitation (pending links and live grants, counted under the invitation's lock). The secret is 32 random bytes (base64url, 43 characters), returned to the owner once, never logged, stored or shown again.
  - (4) **Joining.** `/gabung/<secret>` shows the invitation and the role (`noindex`, `no-referrer`) and accepts only on a POST. Signed out, the secret waits in an HttpOnly, SameSite=Lax cookie scoped to `/gabung` for an hour (Secure over HTTPS), and sign-in or sign-up returns to `/gabung/terima`, whose URL carries no secret. Used, expired, revoked, unknown and malformed links all read "invalid". The owner, an administrator and a current member are refused, each with its own message; two accounts racing one link and one account racing two links end with one grant.
  - (5) **Every request decides.** `invitationAccess` / `accessFor` (`lib/invitation/members-db.ts`) take the stored invitation and the signed-in account: the owner, or a live grant (not revoked, held by a live customer account) whose role holds the capability, and only while `FLAG_TEAM_ACCESS` is on. Every page, action and route that can serve a member asks it first and refuses administrators; both writers check the grant again inside their transaction (the TypeScript writers' `callerMay`, the API's `members::caller_may` after `identity.rs` admits only a live customer). A refusal is the established private 404 (403 for an administrator on a route), and changes nothing.
  - (6) **A stored answer only after access.** Both writers read an idempotency record only inside their transaction, after the caller's current access to that invitation and capability, and answer a concurrent twin from its record in the same checked transaction. The scope is the acting account's id, never the owner's for a member (D-046), so a revoked member's replay, a changed request under a used key and another member's request are refused or judged afresh; a still-authorised caller replays as before.
  - (7) **What each role sees.** Co-hosts and ushers find the invitation under "Dibagikan dengan Anda" on their dashboard with exactly their entries; the desk opens by a full page load (D-056's camera policy). The usher's desk carries each guest's display name, a one-way key of the pass id and the arrival time only: no phone, RSVP, pass id, wish, insight or export. A member leaves their own grant whatever the flag; the owner revokes any row; the member is refused from their next request. A desk left open after revocation gets 404 for its stored batch, which leaves the outbox with a notice that says access ended or passes are off, without saying which.
  - (8) **Off.** `FLAG_TEAM_ACCESS` defaults off. Off is owner-only at every entry (the team page, the join pages and the shared section included) even with live grants and for a form rendered while it was on; grants are kept and work again when it is switched back on. ADR-A3 is unchanged: the check-in route checks the grant instead of ownership.
- **Rejected:** sharing the owner's account or session (no revocation, no attribution); roles in Clerk or Clerk organisations (roles stay in the database, `docs/systems/auth.md`); invitations by email (no delivery integration is live; the owner sends the link); a stored or reversible secret (a database copy would open every pending link); scoping a member's idempotency key to the owner (a member would read the owner's answers, D-046); a flag check in the writers (the flag is a Next.js rollout control; the writers keep the grant check as defence in depth).
- **Limits:** the signed-in path with real Clerk keys is DA-01 item 8, NOT RUN: every s35 browser and API run stubs Clerk. `BACKEND_ROSTER=rust` / `BACKEND_RSVP=rust` / `BACKEND_WISHES=rust` with members are sandbox results. A member sees guest data within their role and can copy it; revocation cannot recall what was seen. A desk device's outbox belongs to the device: whoever next signs in there with check-in access sends it under their own scope (first arrival still holds). There is no audit trail of who checked whom in beyond the CHECKIN rows.
- **Evidence:** E-075.
- **Revisit:** an audit trail per member (ADR-A3's route is the place); plan limits replacing the 20-row ceiling; G-045's logs (owner-only until a role is justified); a hard-delete or purge of accounts (B-031) must end their grants first.

### D-064 — Settlement has one writer per call behind `BACKEND_PAYMENT`, two idempotency layers and one shared decision; a paid settlement writes its entitlement outbox row in the same transaction; checkout takes a key bound to the server's intent (B-039, provider-neutral part; s39)
- **Context [OBSERVED]:** B-039 (G-049) asks for local payments through a licensed PJP; the acquirer and its contract are the owner's (ADR-O03, EXT). s38's writer inventory (`docs/systems/payment.md`) listed the provider-neutral gaps of 09 §8: no Rust settlement writer, no entitlement outbox, no checkout idempotency (a double tap made two PENDING orders with different references), transitions safe by the row lock but not conditional, and the settlement rules in TypeScript only.
- **Decision:**
  - (1) **One entry point, one writer per call.** The webhook route and the administrator's confirmation call `settle`, which selects exactly one writer with `BACKEND_PAYMENT=next|rust` (default `next`) and never falls back to the other. The public webhook stays in Next.js: the rail adapter verifies the provider's signature on the unmodified body before the event reaches a writer. The Rust writer is the private `POST /v1/payments/settlements` behind the service signature; the administrator's authorization stays in the console action.
  - (2) **Two idempotency layers in one transaction.** UNIQUE (rail, event id) on `payment_events` ends a redelivery as a duplicate; the order, locked `FOR UPDATE`, moves only by `where status = 'PENDING'`, so two different events (a webhook and a confirmation) pay once. A refusal (unknown order, another rail, another amount or currency, PAID without an amount) rolls back the event row as well, so the provider's retry is judged afresh. The order's amount, currency and rail are authoritative.
  - (3) **One decision in both languages** (`lib/payment/settlement-decision.ts`, `services/api/src/payment/decision.rs`), pinned by `contracts/vectors/payment-settlement.json` (31 cases: duplicates, a different event on a final order, FAILED / EXPIRED, wrong amount, currency or rail, an unknown order, a theme switched in flight, a legacy order without a theme, deleted and purged invitations, running windows, calendar edges).
  - (4) **B-031 under the same lock.** The activation reads only a live invitation, locked as a deletion locks it. Money on a deleted or purged invitation is recorded (order PAID, its payment and event) and activates nothing; a restore finds the paid order.
  - (5) **Entitlement outbox.** Each paid settlement writes one `payment_settled` row in `jobs` (dedupe `order:<id>`, 20 attempts) in its transaction; `invitesion-jobs` completes it once the order is PAID with the payment it names, and writes nothing. The outbox never publishes (activation stays in the settlement); a repeated delivery reads the same answer; a deleted invitation does not block it; a worker failing midway is taken again after its lease.
  - (6) **Ambiguous outcomes (Rust).** One `Idempotency-Key` per settlement, recorded with the answer inside the settlement's transaction; an unknown outcome (unreachable, timeout, 5xx) is resent once under the same key, so a committed answer replays; still unknown, `SettlementUnconfirmedError`: the webhook answers 500 for the provider's retry and the console asks the administrator to reload.
  - (7) **Checkout key.** The checkout page renders a UUID; `createOrder` stores it with the SHA-256 of the intent the server computed (invitation, theme, tier, amount, currency, rail) under a partial unique index on (customer, invitation, key) (migration 0027, additive). The same key and intent resume a PENDING order with its reference (the rail is asked for the same charge: Stripe's own idempotency key `checkout:<reference>`, a QRIS code derived from the order), report a PAID one and refuse a FAILED or EXPIRED one; another intent conflicts and writes nothing. The provider is called outside any transaction and its handle stored only while the order is PENDING. Stripe customers are sent to Stripe's hosted page (https only).
  - (8) **Rollout and rollback.** 0027, then the B-039 jobs runner, then `BACKEND_PAYMENT=rust` on preview under load, production, seven days within the SLO, and only then the TypeScript writer removed (ADR-A2). Rollback: `BACKEND_PAYMENT=next`. A code rollback to the U5 release runs on 0027; rolling forward releases outbox rows an older runner gave up and enqueues the payments it made meanwhile (runbook: `services/api/README.md`).
- **Rejected:** activating from the outbox worker (an asynchronous activation could publish after a deletion committed in between, or leave a paying customer unpublished); a fallback write to the other writer after an unknown outcome; a checkout key bound to anything the form sends (the price is the server's); a provider-specific PJP adapter now (no acquirer, no contract).
- **Limits:** the PJP adapter, a real Stripe Checkout Session, real money, real-Clerk acceptance of the checkout form and the console (DA-01 item 12) and the `BACKEND_PAYMENT=rust` rollout are owner operations, NOT RUN. Payments made before B-039 have no outbox row.
- **Evidence:** E-082.
- **Revisit:** the PJP adapter behind the rail interface once the acquirer is chosen; retiring the TypeScript writer after its SLO window; receipts (G-050) as the outbox's first consumer.

  - (5) **Overlap with G-044:** a team grant is read only while `FLAG_TEAM_ACCESS` is on and a workspace grant only while `FLAG_WORKSPACES` is on; an account holding both on one invitation gets the broader role, listed once.
  - (6) **Credit ledger: mechanics only** (`lib/workspace/credits.ts`, Next.js its only writer). Every change is one append-only entry (`grant` with a positive delta, `debit` with a negative one, `balance_after` ≥ 0) written with `workspaces.credit_balance` in one transaction under the workspace's row lock, so concurrent operations queue and the balance always equals the ledger. An operation key is UNIQUE per workspace: the same request again replays its entry, another amount or kind under a used key is a conflict, and a debit beyond the balance is refused with nothing written. `debitWith` runs the debit inside its operation's transaction, so an operation that fails takes its debit back. A purge clears an invitation's `client_label` with its content and keeps the ledger rows pointing at the tombstone, like orders (D-063). No checkout, product, grant or top-up path calls the ledger.
  - (7) **`FLAG_WORKSPACES` (off by default).** Off: `/dashboard/workspace` and `/gabung/ruang/*` answer 404, staff hold nothing at any entry and the shell drops the entry; workspaces, memberships, assignments and ledger entries are kept, and turning it on again restores the kept grants unchanged.
  - (8) **Rollout: schema before code.** 0030 follows 0029 and goes before the G-052 release; the G-053 code runs unchanged on 0030 (rehearsed with stored rows), so a code rollback needs no schema step. Rollback: the flag off.
- **Rejected:** moving ownership of an invitation to the workspace (payments, receipts and deletion are the owner's; a reseller's client would otherwise depend on the reseller's account for their money trail); a third role or per-capability grants (the two team roles cover the desk and guest work; content stays with the owner); a ledger without the row lock (the concurrency checks write more debits than the balance holds); pricing, packs, top-ups or a checkout for credits before the owner sets them; white-label domains or branding (not in G-052's scope).
- **Limits:** real-Clerk acceptance of the workspace page, the staff links and the staff's pages (DA-01 item 13) is NOT RUN; credit prices, packs, top-ups, live use, white-label scope and partner self-service are EXT; disabling a workspace has no console yet (a database statement); production activation is an owner operation.
- **Evidence:** E-085.
- **Revisit:** a console to disable a workspace; a credit price and its first consumer once B-040 and G-049 are decided; partner self-service for G-053's affiliates.

### D-068 — A memorial is an occasion declared in the config of a `tasyakuran` invitation, not a seventh event type; the countdown is the host's explicit switch; religious text reaches a page only as an approved corpus entry with its provenance, on the design families (B-032 / I-13, I-11; code s47, verified and closed s48)
- **Context [OBSERVED]:** the catalog's `tahlilan` category (one template today, `149 doa-khusyuk`) maps to the core event type `tasyakuran`, which drives creation, pricing, publishing, entitlements and both writers. Before B-032 a memorial was created and labelled as a thanksgiving (music and gift on, a countdown, "Tentang Syukuran", "Undangan Tasyakuran") and its preset carried a religious opening sentence outside the corpus (ADR-O04). The verified corpus is empty by design. The legacy layout is frozen for compatibility (D-041).
- **Decision:**
  - (1) **Occasion, not event type.** A preset may declare `settings.occasion` (today only `memorial`, from the `tahlilan` category, `lib/invitation/occasion.ts`). The wizard, preview, editor, profile, theme offer and guest page read it for the product's own words; pricing, publishing, entitlements and the writers keep reading the event type. **Absent means the event type's own occasion**, so every invitation stored before B-032, memorials included, renders exactly as before, and reading never writes the key.
  - (2) **Sober defaults for new memorials:** music, gift and countdown off; no preset opening words (the family writes its own; an empty field renders nothing); the first event `Tahlilan & Doa Bersama`; Gapura when F-02 chooses a family; memorial themes only. Every product label is neutral (`MEMORIAL_COPY`), never religious text. A celebration on `tasyakuran` (`syukur-hangat` and the rest) is created exactly as before.
  - (3) **The countdown is the host's explicit switch.** `settings.countdown: false` hides it; absent or `true` shows it as before. It decides the countdown only: the add-to-calendar links stay for a published invitation's future primary event. The editor always sends a boolean.
  - (4) **Religious text by reference only (I-11).** A quote may name a corpus entry by `quote.corpusId`; the editor offers approved entries only and clears a reference with `''` (the merge keeps a key a save leaves out). The design families print the entry's exact text, citation and a provenance line. A pending, withdrawn, unknown or cleared reference renders nothing, never the host's typed text in its place, and the religious-text gate reports it. Entries come from the owner alone, verbatim with complete provenance.
  - (5) **The legacy layout stays frozen (D-041):** it keeps rendering only the stored `quote.text` and author, never an entry or its provenance, and the editor's hint says so on a legacy invitation. Rendering entries on legacy would need a rendered PASS and the owner's approval.
  - (6) **The content facade owns the fields.** `settings.occasion`, `settings.countdown` and `quote.corpusId` live in the strict schema and the merge; the Rust writer stores the prepared config as an opaque value, so neither writer, query, OpenAPI document nor migration changes, and both writers store and refuse alike (proved end to end).
- **Rejected:** a seventh core event type `memorial` (it would fork pricing, publishing, entitlements, creation and both writers for copy and defaults); a migration or backfill marking stored tahlilan invitations (customer content is never rewritten, and an unmarked memorial keeps its exact pages); hiding the calendar links with the countdown (mourners still need the date); rendering the host's typed text when a reference is not approved (it would let unverified text stand where a verified one was promised); seeding any scripture, even as an example (ADR-O04).
- **Limits:** the corpus is empty, so no approved quotation renders anywhere; positive cases use fictional test-only entries. Real-Clerk acceptance of the memorial flow (DA-01 item 16) is NOT RUN. Memorials stored before B-032 keep their countdown and the old preset sentence until the host edits them.
- **Evidence:** E-091.
- **Revisit:** another occasion (for example a death anniversary) when the catalog adds one; corpus entries once the owner supplies and approves them; legacy rendering of entries only with the owner's approval.

### D-069 — An invitation may require a passcode of its guests: the hash lives outside the content, the gate runs before any content query on every guest surface, admission is a path-scoped cookie keyed by the stored hash, and attempts are bounded per invitation and per address (G-047; s51)
- **Context [OBSERVED]:** guest links travel through WhatsApp groups and get forwarded. Before G-047 every published invitation was readable by anyone holding its shared link; only the personal link was a capability (B-011). Hosts asked for a shared code; the backlog row requires that nothing beyond the cover renders without it and that it is rate-limited.
- **Decision:**
  - (1) **Outside the content.** Two nullable columns, `invitations.guest_passcode_hash` and `guest_passcode_set_at` (migration 0031, additive), never `config`: a passcode is never versioned, restored (G-046), sent to the editor or written by either content writer. One writer, `lib/invitation/guest-passcode-db.ts`, behind `PUT` / `DELETE /api/invitations/<id>/passcode` (the owner's session, the flag, the role; 422 `INVALID_PASSCODE`); the answer never carries the hash or the code.
  - (2) **The code:** 6–32 letters or digits, compared NFKC-normalised, trimmed and lower-cased; stored as scrypt (N 16384, r 8, p 1, 16-byte salt) in a self-describing string.
  - (3) **The gate before any content query.** `loadGuestGate` runs once per request before any guest, wish or media query on the shared link, every personal link, the pass and their metadata. A locked page is the cover alone (label and names, never the guest's name) with a plain form to a server action; RSVP and wishes refuse before either writer.
  - (4) **Admission** is the cookie `inv_unlock_<id>` = expiry + HMAC keyed by SHA-256(label ‖ stored hash): HttpOnly, SameSite=Lax, path `/i/<slug>`, 30 days. A change or removal ends every admission; one invitation's admission never opens another; guest pages stay `private, no-store`, so no shared cache serves an admitted response to another visitor.
  - (5) **Bounded attempts,** counted before the code is checked: per invitation (50 / 10 min, from every address) and per keyed address hash (5 / 10 min, needs `INTERNAL_API_SECRET`); a refused window refuses a correct code too.
  - (6) **Side surfaces by policy:** the calendar, both QRIS routes and the child photo answer 404 `private, no-store` while locked (the admitted calendar `private, no-store`); the Story image and the public e-card answer 404 for a protected invitation (cached for everyone, they carry the date); the link card and share metadata are the cover for every viewer (no date, no opening text); I-21's photo routes and upload refuse while locked.
  - (7) **Lifecycle.** `FLAG_GUEST_PASSCODE=off` is the rollback: content and side surfaces return, the editor card hides, the route answers 404, hashes are kept; on again restores the same gate and the same admissions. B-031's purge clears both columns on the tombstone (R-X10).
- **Rejected:** a client-side gate or an overlay (the content would travel in the first response); the code in `config` (versioned, restored, sent to the editor, written by both writers); a per-guest code (the personal link already is one); caching admitted pages.
- **Limits:** a passcode protects the pages, not what an admitted guest saves or forwards; the per-address bound needs `INTERNAL_API_SECRET`; real-Clerk acceptance of the owner card is DA-01 item 19.
- **Evidence:** E-096.
- **Revisit:** a host-chosen expiry or a per-event code; telling the host when the invitation-wide bound trips.

### D-070 — After the event, the invitation's own link may show the host's thank-you and the photos guests share from their personal links; the memory is content, the photos are protected media rows with one writer and the host's review (I-21; s51)
- **Context [OBSERVED]:** competitors reuse the link after the day for a thank-you and guest photos (`03-teardowns/_flows/post-event.md`; S-KAT-003, S-INV-002). I-21 was adopted for later, "after moderation (B-028) and the image pipeline (B-019)". Before I-21 the link showed the same page after the event, and read-only after expiry.
- **Decision:**
  - (1) **Content, opt-in.** `config.postEvent` {`enabled`, `message` ≤ 1,000, `photos`}; both switches optional, absent = off (R-X7: a default would fill a partial save before the merge). Saved, versioned and restored like any section through either content writer (the Rust writer stores the prepared config as an opaque value).
  - (2) **When and where.** The four design families render it once the last event the page's audience may see is over (`endAt`, else start + 6 h), per audience under D-037, so an invite-only event never delays or reveals another audience's memory; the legacy layout never (D-041). Before that the message never travels.
  - (3) **Photos are rows, not content.** A guest photo is a `media_assets` row of type `guest-photo` (no migration): its file under the invitation's protected prefix (D-040), `meta` {`guestId`, `review`, `reviewedAt`}. One writer, `lib/invitation/guest-photos-db.ts`, every statement scoped to one invitation and the type; never in the gallery, the editor or the media library, and a protected URL in the gallery is refused (D-040). G-046 restores and both content writers never touch them.
  - (4) **Who shares, who sees.** A guest shares from their personal link (the link is the identity, as for RSVP and wishes) while the memory is open, photos are on and the invitation still takes writes; 5 photos per guest, 10 uploads an hour; JPG, PNG or WebP by its bytes, up to 5 MB (no GIF, never SVG). Every photo waits for the host; its guest sees and may delete theirs whatever its review; nobody else sees a pending or hidden one. The shared link only views.
  - (5) **Delivery** through `/i/<slug>[/<guest>]/kenangan/<id>`: the G-047 gate first, then a published live invitation, the guest link, the memory open with photos on, and a visible photo or the guest's own; `private, no-store`, nosniff, sandboxed. `/media` serves the file to the owner alone, who reviews on `/dashboard/invitations/<id>/kenangan` (show, hide, delete).
  - (6) **Upload by route, not by server action (R-X8):** `POST /i/<slug>/<guest>/kenangan`, same-origin (ADR-A3), every refusal decided from the link before the body is read; a server action's 1 MB body cap would refuse most phone photos and raising it would raise it for every action.
  - (7) **Lifecycle.** Photos off, memory off, a passcode, deletion (B-031) or the flag off hide everything at once and keep the rows; B-031's purge removes rows and files with the invitation's other media. `FLAG_POST_EVENT_MEMORY` stays **off** by default until the guest-photo notice (B-021) and the retention review (B-031, D-063) cover guest photos.
- **Rejected:** a separate memory page or link (the brief: the existing link); uploads from the shared link (no identity, no cap); publishing guest photos without review (B-028's model); photos in the gallery or `config` (they would be versioned, restored and rendered as host media); a server-action upload (R-X8).
- **Limits:** guest photos get no image variants (protected media never do, D-040); the host is not notified of new photos; real-Clerk acceptance of the review page is DA-01 item 20; uploads from real phones' cameras are EXT.
- **Evidence:** E-097.
- **Revisit:** variants for approved photos once a protected variant path exists; a download of the approved photos for the host; a retention period for guest photos shorter than the invitation's.
