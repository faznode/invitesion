The contract is `openapi.json` (OpenAPI 3.1, generated from the code). Errors are RFC 9457 `application/problem+json` with a stable `code` (`domain.reason`), including timeouts (`request.timeout`); a 422 names its subject (`eventId`, `questionId`) and a 429 carries `Retry-After`. Every response carries `x-request-id` (taken from Next.js or minted here).

## Content (B-035, D-053)
- **One transaction per save:** the owner's invitation row is locked (`for update`), a retry under its key that waited for that lock replays its first attempt's answer, then `max(invitation_versions.version_no)` is read and the shared decision (`contracts/vectors/content-rules.json`, run in both languages) refuses a stale base before judging references and the theme. A write sets `invitations.config`, turns the live row off and inserts the next version row: the statements and order of `lib/invitation/content-next.ts`.
- **Problems:** `content.not_found` (404: not this owner's), `content.version_conflict` (409, with `currentVersion`; nothing written), `content.media_refused` and `content.theme_not_entitled` (422, with `issues`: paths and reasons, never values), `owner.unknown_user` / `owner.role_not_allowed` (403; administrators do not edit).

## RSVP (R-03, D-043)
- **One transaction per write:** the guest row is locked (`for update`), the shared decision (`contracts/vectors/rsvp-decisions.json`, run in both languages) runs on the config read inside the transaction, and status, headcount, answers and per-event answers are set by one UPDATE with the RSVP analytics row beside it. Stored shapes are the TypeScript writer's.
- **Problems:** `rsvp.link_not_found` (404: no published invitation or no guest for the link), `rsvp.closed` (409: `disabled`, `deadline` or `expired`), `rsvp.status_invalid`, `rsvp.event_answer_missing` (+ `eventId`), `rsvp.answer_invalid` (+ `questionId`), `rsvp.override_invalid` (422), `invitation_or_guest.not_found` (404: not this owner's), `owner.unknown_user` / `owner.role_not_allowed` (403), `rate_limit.exceeded` (429).
- **`Idempotency-Key`:** 1–255 visible ASCII characters, recorded with the response in the write's own transaction and kept 24 hours (`api_idempotency_keys`). The same key and request replay the committed answer with `Idempotent-Replayed: true`; the same key with another request is 422 `idempotency.key_reused`. Refusals record nothing. A key replays only inside its scope (D-046): a guest write's scope is the guest its link resolves to (`rsvp:guest:<guest>`, `wish:guest:<guest>`); a host write's is the owner resolved from the verified token, the invitation and the guest or wish (`idempotency::host_scope`, e.g. `wish:host:<owner>:<invitation>:<wish>`). Another customer, another invitation or another resource never reads a cached answer or a 422: the request is judged afresh and the ownership check refuses it (404). The same owner's retry still replays, including a delete whose row is gone. `scripts/verify-host-replay-isolation.ts` proves it against the binary. Next.js sends a key with every write and resends an unknown outcome once under the same key (`lib/invitation/rsvp-writer.ts`).
- **Limits (B-013):** fixed windows in `api_rate_limits`, shared by every instance, checked after a replay and before the transaction: per link (`rsvp:link:<guest id>`) and per address (`rsvp:ip:<HMAC>`). The address is the one Next.js derived by its trusted-proxy contract (`TRUSTED_PROXY_HOPS`); IPv4 counts by address and IPv6 by /64, and only an HMAC of that key under the service secret is stored. Something that is not an IP literal skips the per-address limit (logged without the value).

## Wishes (R-04, D-044)
- **States:** a wish is `VISIBLE` (`is_hidden` false), `PENDING` (hidden and never reviewed: the guestbook was moderated when it arrived) or `HIDDEN` (hidden by the host, `reviewed_at` set). The guest page lists visible wishes only, with the host's reply under them; a hosts-only guestbook (`visibility: host`) lists none. Migration 0017 adds `reviewed_at`, `host_reply`, `replied_at` and the index `guest_messages_invitation_visible_idx (invitation_id, is_hidden, created_at)`, which the guest page's list and count use.
- **One transaction per write:** the guest's wish inserts the row and its `GUESTBOOK` analytics row together; moderation and replies lock the owner's wish (`for update`) and change only its own columns. The shared decision (`contracts/vectors/wish-decisions.json`, run in both languages) decides switch, message, moderation and reply text.
- **Problems:** `wish.link_not_found` (404), `wish.closed` (409: the guestbook is switched off), `wish.message_invalid` / `wish.reply_invalid` (422: empty, over 1,000 UTF-16 units, or U+0000), `invitation_or_wish.not_found` (404: not this owner's invitation or not its wish), `owner.unknown_user` / `owner.role_not_allowed` (403), `rate_limit.exceeded` (429).
- **`Idempotency-Key` and limits** as for RSVP: the guest page mints a key per rendered form (`lib/invitation/rsvp-form-key.ts`), the writer one per host action; limiter keys `wish:link:<guest id>` and `wish:ip:<HMAC>`. A key reused with another message is a new wish to Next.js (an old page brought back and changed), sent under a fresh key.

## Roster (B-033, D-052)
- **What it owns:** every writer of `guests`' roster columns and rows (name, phone, category, guest_count, slug, link_token, invited_event_ids, sent_at, checked_in_at with its CHECKIN analytics row, import_batch_id), `guest_registrations` and `guest_registration_links` (migration 0019, additive). The RSVP columns stay with R-03 and `opened_*` with R-02; nothing here touches them.
- **Same rows whichever writer:** the rules are one module per language run against `contracts/vectors/roster-rules.json` (rows, B-018 numbers, slugs, whole imports, self-registrations, ceilings, and the limiter's address keys, buckets and limit strings), and both writers take the same transaction-scoped advisory lock per invitation (namespace `0x524F5354`, "ROST"), so a flip of `BACKEND_ROSTER` never interleaves two writers on one roster. Owner writes check the invitation's owner inside their own transaction.
- **Ceilings (technical, until a plan limit exists):** 3,000 guests per invitation, 1,000 rows per import, 300 waiting registrations, 50 seats per guest and 5 per self-registration.
- **Problems:** `roster.not_found` (404: not this owner's invitation, guest, batch or registration), `roster.row_invalid` (422, `reason`: `name`, `phone`, `seats` or `category`), `roster.full` (409), `roster.invite_invalid` (422), `roster.duplicate` (409: an approval whose person is already a guest; the request stays), `registration.link_not_found` (404), `registration.closed` (409: the invitation is no longer published), `registration.full` (409), `owner.unknown_user` / `owner.role_not_allowed` (403), `rate_limit.exceeded` (429).
- **Keys and limits:** host writes are scoped `roster:<operation>:<owner>:<invitation>:<resource>` (`roster:undo:<batch>:…` for an undo); a self-registration's scope is `registration:link:<invitation>`. Limits `registration:link:<invitation>` and `registration:ip:<HMAC>`, defaults 20 and 5 per 600 s (`RATE_LIMIT_REGISTRATION_LINK`, `RATE_LIMIT_REGISTRATION_IP`); the TypeScript writer counts in the same rows, so a limit holds across a flip.
- **Guest passes (B-024, D-056):** the pass rules are `src/roster/pass.rs`, the port of `lib/invitation/guest-pass.ts`, run against `contracts/vectors/guest-pass.json`. A check-in batch takes the roster lock and locks each pass's guest, so two desks scanning one guest record one arrival. Its key is scoped `roster:pass-checkins:<owner>:<invitation>:0`, and the TypeScript writer records under the same scope and request hash (`lib/idempotency.ts`), so a batch replays its first answer across a flip of `BACKEND_ROSTER`. Problems: `guest_pass.not_enabled` (409: the invitation has not opted in), `guest_pass.not_configured` (503: no secret; answered before any write, so Next.js never resends it), `roster.not_found` (404), `idempotency.key_reused` (422). The browser never calls this endpoint: the scanner posts to the same-origin Next.js route (ADR-A3).

## Team members (G-044, D-057)
- **Who may write.** Every host write (the nine roster writes, the RSVP override, wish moderation and reply) accepts the invitation's owner or a member whose live grant in `invitation_members` (migration 0023) holds the operation's capability: `src/members.rs`, the port of `lib/invitation/members.ts`, pinned by `contracts/vectors/member-roles.json` (co-host: check-in, guests, wishes; usher: check-in). `identity.rs` admits only a live customer account; `members::caller_may` then decides inside the write's own transaction. Grants are minted, accepted and revoked by Next.js only; this service reads them.
- **Stored answers after access.** A host write reads its idempotency record on its own transaction (`idempotency::replay(&mut *tx, …)`) only after `caller_may`, so a member whose grant was revoked, another account or another invitation is refused (404) and never replays a cached answer or learns that the key exists; a concurrent twin is answered from its record in the same checked transaction. Scopes carry the acting account's id, never the owner's for a member (D-046).
- **Not here.** `FLAG_TEAM_ACCESS` is a Next.js rollout control: Next.js refuses members at every entry while it is off, and this service keeps the grant check as defence in depth.

## Payments: settlement and its outbox (B-039, D-064)
- **The statements and order of `applySettlement`** (`lib/payment/service.ts`), in one transaction: the event row (`payment_events`, UNIQUE rail and event id; a conflict answers `duplicate` and ends there); the order locked by its reference and its id written on the event; the shared decision (`src/payment/decision.rs`, the port of `lib/payment/settlement-decision.ts`, both run against `contracts/vectors/payment-settlement.json`); a refusal rolls everything back, the event included, so the provider's retry is judged afresh. FAILED / EXPIRED: `update orders … where status = 'PENDING'`. PAID: the invitation read `for update` with `deleted_at is null` (the lock a deletion takes), the conditional transition, the payment row, the activation only when the decision allows it, and one `payment_settled` row in `jobs` (dedupe `order:<id>`).
- **Problems:** `payment.invalid_rail`, `payment.invalid_event` (400), `payment.order_not_found` (404; nothing kept), `payment.rail_mismatch`, `payment.amount_unverifiable`, `payment.amount_mismatch` (409; nothing kept), `idempotency.key_reused` (422). Answers name the order id and the activation, never personal data.
- **`Idempotency-Key`:** scope `payment:settlement`, recorded with the answer in the settlement's transaction. Next.js mints one key per settlement and resends an unknown outcome once under it (`lib/payment/settlement-api.ts`); a committed answer replays, another body under the key is 422; still unknown, Next.js reports `SettlementUnconfirmedError` and the webhook answers 500 so the provider retries. Nothing falls back to the TypeScript writer.
- **Outbox delivery (`payment_settled`, `src/payment/outbox.rs`):** done when the order is PAID with the payment the payload names and its receipt is issued (G-050, below); it writes nothing to orders, payments or invitations. Repeated after an expired lease or by a second runner: the same read, and the receipt is found, not issued again. A deleted or purged invitation does not stop it (orders, payments and receipts are kept). A payload or row that cannot be right is given up naming the order id. It never activates or publishes: that stays in the settlement's transaction under the row lock.
- **Receipts (G-050, D-065, `src/payment/receipt.rs`, migration 0028):** this runner is the only writer of `receipts`. One per order, copied in one transaction from the order and its PAID payment (owner, reference, tier, amount, currency, rail, the provider's transaction id, `paid_at` or, for an older row, the payment's own time), numbered by `insert into receipt_counters … on conflict (scope) do update set last_number = last_number + 1 returning last_number`, whose row lock lasts to the commit: numbers follow commit order without gaps. An order that has its receipt takes no number; a concurrent delivery of the same order yields at `on conflict (order_id) do nothing` and rolls back its increment. Next.js reads receipts for their owner only and, on the owner's request for an earlier payment, writes or re-arms that order's `payment_settled` row (`lib/payment/receipts.ts`); `FLAG_RECEIPTS` gates the pages, never the issuing. `scripts/verify-receipts.ts` proves it against both writers and two concurrent runners.
- **Receipts: rollout order and recovery (G-050, D-065 (7); rehearsed in s40 on a populated database):** deploy migration 0028 before a G-050 `invitesion-jobs`; `FLAG_RECEIPTS` gates only the owner surfaces and cannot protect a runner that starts first. Such a runner fails a waiting `payment_settled` row on the missing `receipts` relation, writes nothing else and retries it later; a given-up row is not taken. After 0028 the row is delivered with the next number; a row given up meanwhile is re-armed by the owner's request (`lib/payment/receipts.ts`) or by the statement below. **Code rollback to B-039 on the 0028 schema:** the B-039 runner completes `payment_settled` rows without receipts, and their orders read as on request. **Roll-forward**, from the rollback time `<since>`: `update jobs set done_at = null, attempts = 0, run_at = now() at time zone 'utc', locked_until = null, last_error = null where kind = 'payment_settled' and done_at >= '<since>' and not exists (select 1 from receipts r where 'order:' || r.order_id = jobs.dedupe_key)`; the G-050 runner then issues them with the next numbers (s40: exactly the two rollback-window rows, receipts 9 and 10, numbering 1–10 without a hole).
- **Roll-forward after a code rollback to a release without B-039** (rehearsed in s39 on a populated database): (1) an older runner gives up `payment_settled` rows as `unknown job kind`; release them: `update jobs set attempts = 0, run_at = now() at time zone 'utc', last_error = null where kind = 'payment_settled' and done_at is null and last_error = 'unknown job kind'`. (2) Orders the older writer paid meanwhile have no outbox row; enqueue them once, from the rollback time `<since>`: `insert into jobs (kind, payload, dedupe_key, run_at, max_attempts) select 'payment_settled', jsonb_build_object('orderId', o.id, 'paymentId', p.id, 'invitationId', o.invitation_id, 'templateId', o.template_id, 'activation', 'backfilled'), 'order:' || o.id, now() at time zone 'utc', 20 from orders o join lateral (select id from payments where order_id = o.id and status = 'PAID' order by id limit 1) p on true where o.status = 'PAID' and o.paid_at >= '<since>' on conflict (kind, dedupe_key) do nothing`. Payments from before B-039 are not enqueued (G-050: earlier payments on request).

## Jobs runner: purge and retention sweep (B-019, B-031, D-063)
`invitesion-jobs` (`src/bin/jobs.rs`) runs due rows of the Postgres `jobs` table: one pass per invocation (cron), or a pass every minute with `--watch` (the container fallback). It needs `DATABASE_URL` (or `POSTGRES_URL`) and the upload store Next.js uses: all four `S3_*` (`S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, plus `S3_ENDPOINT` / `S3_FORCE_PATH_STYLE` / `S3_SESSION_TOKEN` as needed) or `UPLOAD_ROOT`; a partial S3 set, or neither, refuses to start (exit 2). Each pass prints one JSON line, e.g. `{"claimed":2,"done":1,"retried":1,"gaveUp":0,"swept":0,"storage":"local"}`; exit 1 is a failed pass. Kinds: `image-variants` (B-019), `invitation_purge` (B-031) and `payment_settled` (B-039, above); an unknown kind is given up with `unknown job kind`. Claims are leased (`for update skip locked`), so concurrent runners share the work, and every job is at least once.
- **Deletion (Next.js).** With `FLAG_INVITATION_DELETION=on` and `INVITATION_DELETION_WINDOW_DAYS` set, the owner deletes from `/dashboard/invitations`: one transaction sets `deleted_at` and `purge_after = deleted_at + window` (migration 0026) and queues `invitation_purge` with payload `{ invitationId, deletedAt }`, dedupe key `invitation:<id>:<deletedAt in ms>`, `run_at = purge_after` and 20 attempts (`contracts/vectors/invitation-purge.json` pins the shape in both languages). From then on every guest surface and every writer in both languages answers as for a missing invitation (404, `not_found`; `deleted_at is null` in every statement, enforced by `tests/b031-retention.test.ts`). The owner restores, even with the flag off, until the purge commits; both take the invitation's row lock.
- **Sweep.** Each pass first runs the retention sweep: invitations whose `expires_at` is at least `INVITATION_RETENTION_DAYS_AFTER_EXPIRY` days ago are deleted as their owner would delete them (the window opens and the same job is queued), at most `JOBS_BATCH` per pass. It does nothing unless **both** durations are set. While both stay set, an expired invitation its owner restores is deleted again by the next pass with a fresh window (D-063, open question Q3); nothing is purged sooner than a whole window after the latest deletion.
- **Purge, phase 1 (one transaction).** At `purge_after` the job locks the row. A `deleted_at` other than its payload's (restored, or deleted again later) or a purged row ends it without changes; a job claimed early (clock skew) waits. Otherwise it collects every key under the invitation's own prefixes (`<id>/`, `variants/<id>/`, `protected/<id>/`: listed, so orphans count, and referenced by its rows), keeps any key another unpurged invitation, its versions, another invitation's media or a template still refers to, then deletes the replay records (guest scopes and host scopes naming it), every row of `PURGED_TABLES` (15 tables, children first), its queued `image-variants` jobs, clears `config` and `creation_key`, sets `purged_at` and records `objects` and `keptShared` in its own payload.
- **Purge, phase 2 (storage).** The recorded objects are deleted (a missing object counts as deleted). If any deletion fails, the job retries with backoff (2 minutes doubling to an hour, about fifteen hours over 20 attempts), and a retry goes straight to the recorded objects: rows are never purged twice and the invitation never reopens. After the last attempt the job keeps `last_error` for the operator.
- **Kept.** The tombstone row (the slug stays reserved), `orders`, `payments` and `payment_events` (accounting; their own retention is an owner and counsel decision) and the customer's `conversations`, `messages` and `customer_session_summary` (`RETAINED_TABLES`), all still pointing at the tombstone.
- **Dry run.** `invitesion-jobs --plan-purge <id>` prints one JSON line describing what the purge would do now, from a read-only transaction, and runs no job: `state` (`live`, `scheduled`, `due` or `purged`), `purgeAfter`, `rows` per purged table, `idempotencyRecords`, `variantJobs`, `objects` (to delete), `keptShared` (kept: something else refers to them) and `retained` per kept table. An unknown id exits 2. A live demo invitation with two wishes and nothing uploaded reads `{"invitationId":1,"state":"live","purgeAfter":null,"rows":[{"table":"analytics_events","rows":0},{"table":"guest_messages","rows":2},…,{"table":"guests","rows":5}],"idempotencyRecords":0,"variantJobs":0,"objects":[],"keptShared":[],"retained":[{"table":"orders","rows":0},…]}`.
- **Operating it.** Before anything is switched on: migration 0026 deployed, the runner scheduled against the same database and storage as Next.js (S3 credentials with list and delete), and both durations approved. Read a purge with `--plan-purge` before it is due. A job at its last attempt keeps its error: fix the cause, then `update jobs set attempts = attempts - 1, run_at = now() at time zone 'utc' where id = <job>` lets it try once more, and a job that already recorded its objects only deletes objects. Rollback: the flag off hides deletion (restore stays), unsetting either duration stops the sweep; neither undoes a purge. A purged invitation cannot be restored from the application: recovery is a database and storage backup restore (owner operation), after which the deletion would be repeated.
- **Limits.** Copies outside the origin are not reached: images a browser or a network cache already saved (public uploads are served `public, max-age=31536000, immutable`), downloaded CSVs and PDFs, screenshots. No CDN purge is issued. The durations, the owner's notice text (B-021) and the retention of accounting records wait for the owner and counsel (UU PDP review, EXT).

## Rules
- **One writer per column group.** A domain moves every writer of its columns at once; `BACKEND_<DOMAIN>` selects exactly one implementation per call, with no fallback to the other (`lib/backend.ts`, `lib/invitation/view-writer.ts`, `lib/invitation/rsvp-writer.ts`, `lib/invitation/wish-writer.ts`, `lib/invitation/roster.ts`).
- **drizzle-kit owns migrations.** Nothing here runs DDL. Queries are compile-time checked (`sqlx::query!`) against a database migrated by drizzle-kit; the metadata in `.sqlx/` lets builds run without a database (`SQLX_OFFLINE=true`). The API's own operational tables (migration 0016: idempotency keys, rate limits) and the wishes columns and index (0017) are drizzle migrations too.
- **Shared behaviour is proven by shared vectors** run in both languages: `contracts/vectors/service-signature.json` (expected values from an independent implementation), `view-dedupe.json`, `rsvp-rules.json`, `rsvp-decisions.json`, `wish-decisions.json`, `roster-rules.json`, `guest-pass.json` and `payment-settlement.json`.
- **Not browser-facing (ADR-A3).** Browser writes go through same-origin Next.js routes, never here. No CORS; every call except liveness is signed: `x-invitesion-signature: t=<unix>,v1=<hex HMAC-SHA256 of t.METHOD.path_and_query.sha256hex(body)>` over the path exactly as sent (percent-encoded segments included), 60 s skew, two secrets during a rotation. Bodies are bounded to 1 MiB (Next.js's server-action limit) and verified before any extractor.

|---|---|---|

| `DATABASE_STATEMENT_CACHE` | no (0) | Prepared-statement cache; keep 0 behind a transaction pooler |
| `RUST_LOG` | no | Log filter (default `info,sqlx=warn`); logs are JSON lines |

Deletion needs `FLAG_INVITATION_DELETION=on` and `INVITATION_DELETION_WINDOW_DAYS` in Next.js and the jobs runner scheduled; the sweep needs both durations in the runner.

## Deployment (owner steps, not done from the sandbox)
- A separate Vercel project with root directory `services/api` (the Rust runtime is beta on Fluid compute); `vercel.json` sends every path to `api/index.rs` and pins `sin1` beside the database. Fallback: the same binary as a container (`src/main.rs`).
- R-01's remaining acceptance: the preview deployment answers health within SLO and records its cold start; trace export once a collector endpoint is chosen.
- Each slice's rollout: `BACKEND_<DOMAIN>=rust` on preview under load, then production, 7 days within the error budget, then the TypeScript writer is removed. RSVP, wishes and the roster also need `OWNER_TOKEN_*` (the Clerk issuer and JWKS) for the host's operations. Rollback at any point: `BACKEND_<DOMAIN>=next`; nothing to migrate back (the columns are shared, 0016's tables are the API's own, and 0017 and 0019 are additive).
- The jobs runner (B-019, B-031): a scheduled invocation of `invitesion-jobs` (or the container with `--watch`) against the production database and storage. B-031 rollout, in order and only after the owner and counsel approve the durations and the notice text: migration 0026 (additive; existing rows untouched), the runner scheduled, `INVITATION_DELETION_WINDOW_DAYS` in both Next.js and the runner, then `FLAG_INVITATION_DELETION=on` on preview with a real Clerk owner, then production; `INVITATION_RETENTION_DAYS_AFTER_EXPIRY` last, after a `--plan-purge` read of what the first sweep would schedule. Rollback as in the jobs section; a purge is never rolled back by configuration.
